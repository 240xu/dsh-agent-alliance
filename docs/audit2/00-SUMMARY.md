## 二、修复清单（按提交顺序）

### 1. `2f6660e` — 五个直接造成金钱/数据损失的缺陷
- **jobs**：`startJob` 与面板圆桌未加保护地调 `jobs.start()`；缺 controller 时抛错，后台功能直接不可用
- **resume 守卫**：原先在 `startActivation` 之后，被拒的续聊仍付一次完整进程启动
- **取消**：信号量快路径不看 `signal.aborted`，已取消的调用仍启动真实调用
- **导入标题**：无用户文本的会话写出后**读不回来**（`session/title` 的 `messageSeqs` 不变量被我写反了）

### 2. `b5693d8` — CLI 错误被当成功 / 台账竞态
- 四家 provider 原先只在"非零退出**且**无输出"时失败。`codex`/`opencode` 把 "quota exceeded" 打到 stdout，
  于是失败被当成功，圆桌报"3 家全部成功"而其中两家只输出了错误字符串，还被当作观点喂给其他成员
- 台账竞态：8 个并发导入只剩 1 条记录，丢失的条目让幂等失效，同一会话被重复导入

### 3. `3837623` — 圆桌成本与并发
- 第 2 轮 prompt 改为以问题本身开头（共享前缀从 **0 字符** 变为完整问题，模型估算 **−21%**）
- 排除成员自己的上一轮发言（此前被标成"其他 agent 的观点"）
- 圆桌纳入 `maxConcurrent`（此前完全绕过）

### 4. `446a5f9` — /state 谎报可用性
四家 provider 一律报 `available: true`，实测 `detectAll()` 说全部不可用。改为真实探测 + 30s TTL。

### 5. `f6eaf59` — **修复我自己引入的四个缺陷**（A2 发现）
- try/catch 太宽，把"容量上限"也吞成内联执行（会占满 20 分钟前台预算且无法取消）

- resume 守卫放错了位置，掩盖了"provider 已注销"的真实原因

### 6. `1b15214` — SQLite 句柄泄漏
每次 `listSessions`/`readSession`/`exportSession` 漏一个 fd，成功与错误路径都漏。
实测 50 次调用 → 修复前 +50，修复后 **0**。

### 7. `e6054d7` — 信号量漂移（critical，A3 发现）
被提升的队列项没有占回槽位，导致**第二次圆桌就跑到双倍并发**（2→4→4）。
现有并发测试只测单批次，所以 196 个测试全部放过它。

### 8. `15bc8c8` — 无主任务、挂起的 runner、丢失的 prompt、探测风暴
- **`agent.sessionId` 字段不存在**（Agent 只有 `id`），所有后台任务静默变成**无主**：
  收不到完成通知、Agent 销毁时不取消、任何会话都能通过 `jobs.list(undefined)` 看到并杀掉它。
  测试没抓到，因为假 Agent 自己发明了 `sessionId` 字段
- job 取消不保证终结：producer 忽略 signal 时任务永久卡在 `stopping`
- `runner` 只监听 `close`，孙进程持有管道时永久挂起并占死一个并发槽
- zcode 模板用字符串替换，prompt 里的 `$&`/`$$` 被当成替换模式而丢失
- 探测串行 + 无并发合并：最坏 50 秒、并发请求各自 fork 一套探测

## 三、权威核实的关键结论（C1）

**21% 的算术正确**，独立重算吻合。但对**四家厂商**套用 Anthropic 的费率是错的：

| 比率 | 审计假设 | 实际 |
|---|---|---|
| cache write | 1.25× | Anthropic 1.25×/2×；OpenAI GPT-5.6+ 1.25×/2.5×；**OpenAI ≤5.5 免费** |
| cache read | 0.1× | 新 Claude 0.025×/0.05×；**gpt-4.1 是 0.25×** |
| output | 5× | Claude 与 gpt-5.6 准确；**gpt-5/codex 是 8×** |

遗漏项：**最小可缓存前缀**（Anthropic 最高 4096）。`S+P ≈ 12,800` 能过，但**低于阈值时缓存会静默失败**
（`cache_creation_input_tokens: 0`），此时"修复"会变成 +17.4% 的陷阱。
正确门控是 `R≥2 && S+P ≥ minPrefix(model)`，不是只看 `R≥2`。

**两条被主源推翻的结论**：
1. 子进程缓存隔离——**错**。缓存按 account/workspace/model 划分，**不按进程**。结论（默认配置省 0%）
   仍成立，但原因是四家**厂商**不同，不是进程隔离。
2. "跨厂商辩论多是冗余"——**不被证据支持**。Zhang et al. 2025 发现同质 MAD 常不如 CoT/自一致性，
   而"模型异质性"是普遍解药。成本论点有 Smit et al. 支持，冗余论点应撤掉。

## 四之二、需要你决策的一项（不是缺陷，是取舍）

**Q1：官方 bundle 启用后，模型会同时看到 `subagent_codex` 和我们的 `agent_dispatch`。**

D1 的建议是**移除默认的 `subagentProvider: 'codex'` / `'claude-code'`**，让官方工具成为唯一官方路径，
`agent_dispatch` 退回 CLI-only；但**保留** codex CLI 后端（面板/HTTP 没有 Agent 身份，只能走 CLI）。

支持移除的证据：
- 官方 `tool-subagent` 会注册一段 system prompt（"start independent delegations … together and
  continue useful work while they run"），与我们的阻塞语义**相反**；模型在发现阶段会结构性偏向官方工具。
- 两个工具共享 subagent 池（8 槽），我们只保证自己那 3 个，真实上限 ≈ 3 + 模型直接调官方的数量。

反对移除的证据：
- 我们的 `agent_dispatch` 是**同步取答案**，官方工具是"发了就继续干活、稍后通知"。这是真实的能力差异，
  不是重复。
- 移除默认值会让**已经配置好官方后端的用户**在升级后静默退回 CLI（CLI 可能根本没装）。

**我没有改这个默认值**——它改变所有用户行为，且两种选择都站得住。请你决定；改起来是一行
（`src/config.js:18-19`），并在 README 说明迁移。

## 五、方法论教训（值得记住的）

**对抗审计不是可选步骤。** 本轮 3 名对抗审计在我的产出里找到 6 个缺陷，其中 2 个 critical；
而单向审计（第一轮）在同样代码里一个都没找到。原因很直接：**审计自己的代码等于给自己盖章**。

**假对象比宿主更聪明是系统性风险。** `agent.sessionId` 与 `ctx.get('logger')` 是同一个根因：
测试里的 fake 提供了宿主根本不存在的字段/方法，于是测试永远绿、生产永远错。
已修正所有假 Agent 形状，并把断言改为针对字段名而非值。

**并发正确性需要多批次测试。** 信号量漂移在单批次测试里完全不可见——第一个批次永远正确。
所有限流逻辑的测试都必须至少跑两轮，且要有重叠批次。
